# Lovable capability benchmark

Verified: **2026-11-26**. Scope: Lovable's documented, user-facing web-app workflow, using only `lovable.dev` and `docs.lovable.dev`. This is a documentation review, not a hands-on validation or a claim about Software Factory's implementation. No existing research-note directory/convention was present; this note establishes `docs/research/`.

## Essential MVP flow

The prioritization here is an assessment for comparison, not a Lovable product tier: a builder should be able to describe an app, review and refine a working preview, add persistent data and login, publish a stable URL, and recover from an unwanted edit. Lovable documents this overall natural-language build, iterate, deploy lifecycle. [Product overview](https://docs.lovable.dev/introduction/welcome)

| Capability | Verified Lovable behavior |
| --- | --- |
| Prompt-to-app conversation | A persistent project chat accepts plain-language requests and file attachments. **Build** changes the app; **Chat** discusses it without editing; **Plan** investigates and prepares an approach before implementation. Context carries across modes. [Project chat](https://docs.lovable.dev/features/projects/chat.md) |
| Visible execution and repair loop | Build mode explores the codebase, changes multiple files, investigates errors/logs/network activity, and verifies results. Activity cards and a Details view expose tasks, tool calls, and file diffs. Follow-up messages can steer a running build. [Build mode](https://docs.lovable.dev/features/agent-mode.md) |
| Interactive preview | The editor runs an updating, clickable app beside chat, with desktop/tablet/mobile sizes, page navigation, refresh/restart, and shareable preview links. The published app remains on its last published version. **The main preview and published app share backend data.** [Preview](https://docs.lovable.dev/features/projects/preview.md) |
| Point-and-edit UI | The preview toolbar offers element selection with a prompt, inline text editing, drawn annotations, and element-pinned comment threads. It replaces the older **Visual edits** panel; current styling changes use selection plus natural language rather than direct color/font/spacing controls. Available on all plans; prompted changes consume build credits. [Preview toolbar](https://docs.lovable.dev/features/preview-toolbar.md) |
| Persistent backend | Lovable's built-in backend provisions database, authentication, file storage, realtime, and serverless functions without a separate Supabase account. It uses Supabase's open-source foundation. Builders can access data, users, storage, jobs, secrets, logs, and usage in the editor. Backend actions have allow/ask/deny permissions. [Built-in backend](https://docs.lovable.dev/features/cloud.md) |
| App login and data access | A login request generates sign-up/login pages connected to the backend and row-level security. The Users view manages app users and sign-in methods. Email/password, Google, and Lovable are documented defaults; further providers and enterprise identity options are supported. Authentication and row permissions are distinct controls. [Authentication](https://docs.lovable.dev/features/authentication.md) |
| Secure service credentials | Chat can request credentials through a secure input. Project secrets are encrypted, write-only after saving, and injected into edge functions rather than exposed to the browser. Secrets have a management UI; Enterprise build secrets are a separate workspace-level facility. [Secrets](https://docs.lovable.dev/features/secrets.md) |
| Publish and update | The Publish dialog deploys to a `lovable.app` URL with managed hosting and HTTPS, shows deployment progress, and provides the live link. Later frontend changes require **Publish changes**. Publishing can also be requested in chat, subject to approval/settings. Unpublishing is supported. [Publish](https://docs.lovable.dev/features/publish.md) |
| History and recovery | Each change creates a version. Builders can preview versions, inspect diffs, bookmark stable states, identify the published version, and revert. Revert restores code and matching edge functions, **not database data or migrations**; very old versions can remain previewable but unrestorable. [Version history](https://docs.lovable.dev/features/projects/history.md) |

## Broader parity

These extend the core loop; their existence does not mean each is necessary for an initial product.

| Area | Verified extensions and relevant boundaries |
| --- | --- |
| Code ownership and Git | Automatic two-way sync with **GitHub, GitLab, and Bitbucket** is available on all plans. Linking creates a new repository; Lovable syncs one active branch at a time and supports creating/switching branches. Local IDE edits can return through Git. [Git sync](https://docs.lovable.dev/integrations/git-sync-overview.md) The in-app code editor supports file/line references, search, and manual edits; editing and full-codebase ZIP download require paid plans. [Code editor](https://docs.lovable.dev/features/code-mode.md) |
| Safe exploration | Drafts provide separate chat, preview, and edits, with accept/delete workflows on all plans. Built-in-backend drafts usually get their own backend with example data, but some share the live backend. Secrets and connected services retain live values. Accepting a draft can immediately change production schema/functions before frontend publishing. [Drafts](https://docs.lovable.dev/features/drafts.md) |
| Collaboration and review | Project/workspace invitations, roles, and real-time visibility support teams; collaborators consume the owning workspace's credits. [Collaboration](https://docs.lovable.dev/features/collaboration.md) View-only preview links can work without a Lovable account; passwords/custom expiry and restricted project visibility require Business/Enterprise. Free/Pro preview links expire after seven days. Project access and published-site access are separate. [Sharing](https://docs.lovable.dev/features/share-project.md), [Plan matrix](https://docs.lovable.dev/introduction/subscription-plans.md) |
| Domains and audience | Paid plans can connect an existing domain, buy one through Lovable, or transfer registration. Lovable-managed registration includes DNS and SSL setup; Enterprise supports a shared publishing domain across apps. [Domains](https://docs.lovable.dev/features/custom-domain.md) Published apps can be public or invite-only; workspace-wide audiences are Business/Enterprise. [Publishing audience](https://docs.lovable.dev/features/publish.md) |
| Connectors and APIs | Three distinct connection models: shared **app + chat** connections; personal **MCP chat** context that is absent from the published app; and **app user** connections using each visitor's account/permissions. The catalog includes tools such as Slack, Notion, HubSpot, and Google Workspace. Custom REST connectors, custom MCP servers, and direct API integrations cover uncatalogued services. [Connector overview](https://docs.lovable.dev/integrations/introduction.md) |
| Payments and app AI | Paid built-in payments support subscriptions/one-time purchases through Paddle or Stripe, with separate preview test and published live environments; merchant verification is needed to go live. [Payments](https://docs.lovable.dev/features/payments.md) Built-in app AI supplies chat/summaries, images, video, music, semantic search/RAG, classification, and speech without separate provider credentials; app AI is distinct from the coding agent. [App AI](https://docs.lovable.dev/features/ai.md) |
| Persistent context | Workspace, project, and personal instructions apply across messages on all plans. Lovable also reads project `AGENTS.md`/`CLAUDE.md`; on-demand skills complement always-included instructions. [Instructions](https://docs.lovable.dev/features/knowledge.md) |
| Verification and ongoing care | Browser testing interacts with real flows and observes console/network signals; frontend tests and direct/automated edge-function verification are available. Tests for changed business rules can be generated automatically; edge tests require a request. [Testing](https://docs.lovable.dev/features/testing.md) Paid **project monitoring**, currently beta, checks code, visitor errors, and connector failures on a schedule, emails important findings, and routes fixes into chat. [Monitoring](https://docs.lovable.dev/features/project-monitoring) |
| External agent interface | Lovable's MCP server lets external AI clients create projects, send build requests, inspect code/history, use drafts, and deploy. Available on all plans, with OAuth permissions and workspace controls; calls act on real projects and consume credits. [Lovable MCP server](https://docs.lovable.dev/integrations/lovable-mcp-server.md) |

## Operations, security, and commercial controls

- **Security is an explicit product surface.** Automatic checks cover database/RLS settings, vulnerable dependencies, and unauthenticated public MCP tools. Advanced checks inspect application code. Findings have severity levels and can be sent to the agent to fix. Checks are not a security guarantee. Publishing with findings can be allowed unless workspace controls block it. Business/Enterprise add a workspace security center; recurring scans are Enterprise. [Security overview](https://docs.lovable.dev/features/security.md)
- **Enterprise governance is broader than app auth.** The plan matrix lists Business/Enterprise SSO and training-data exclusion by default; Enterprise adds SCIM, audit logs, log exports, organizations, publishing/sharing controls, and EU inference. Free/Pro accounts can opt out of training use. These are plan-specific controls, not universal defaults. [Plan matrix](https://docs.lovable.dev/introduction/subscription-plans.md)
- **Diagnostics and recovery have separate scopes.** Searchable backend logs cover server/functions, PostgreSQL, authentication, realtime, and storage; the viewer refreshes rather than streaming. [Logs](https://docs.lovable.dev/features/logs) Daily database backups retain roughly 14 days; restore replaces schema/data and entails downtime. Database export includes user records/password hashes but excludes storage files, secrets, provider settings, and function code. This is separate from code history and is not whole-app recovery. [Backups and exports](https://docs.lovable.dev/features/database-backups.md)
- **Metering joins build and runtime costs.** One workspace credit balance funds build, chat, Cloud, app AI, and managed connector usage, with usage-specific grants applied first. Build/Run are reporting categories rather than separate balances; published hosting itself is free. Build mode pricing depends on work performed. Pro/Business support one-time and automatic top-ups. [Credits](https://docs.lovable.dev/introduction/credits-and-usage.md), [Plans](https://docs.lovable.dev/introduction/subscription-plans.md)
- **Spend controls can affect live service.** Paid owners/admins can set daily/monthly thresholds and notification/blocking actions at workspace/project/member scope; group/token controls have additional plan restrictions. Run limits can pause backend, AI, and metered connectors in deployed apps. [Usage limits and alerts](https://docs.lovable.dev/features/usage-limits-and-alerts.md)

## Interpretation limits

The useful benchmark is the integrated user journey, not merely whether underlying infrastructure exists. The MVP/parity split above is an analytical prioritization; a local gap assessment needs separate repository evidence. Documentation verifies advertised workflows and restrictions, not generation quality, reliability under load, security effectiveness, or measured deployment latency. Prices, credit grants, feature gates, and beta status should be rechecked before making commercial commitments.
